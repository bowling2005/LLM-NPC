# 《港口宝石失窃案》台词库数据结构设计

> 基于 `/Users/ouyang2005/Desktop/粗略剧本.txt`（身份版）设计
> 玩家交互模型：在每个决策点从 a / b / c / d 四个选项中做选择以推进剧情

---

## 一、设计前提：从剧本里提取出的硬约束

台词库不是"一堆句子"，它必须能承载剧本已有的这几个机制。先把它们列清楚，结构才有依据：

| 剧本机制 | 原文依据 | 对数据结构的要求 |
|---|---|---|
| 七日流程，每天 3 次行动 | "第一天…（行动3次）" | 台词要挂 `day` + `slot`，且需要"行动配额用尽"的兜底台词 |
| 强制节点不可跳过 | F1（D1傍晚酒馆）、F2（D4宅邸）、F3（D7法庭） | 需要 `trigger.type = forced_node`，条件恒真、优先级最高、`once = true` |
| 搜证是"多选 N 处"而非单选 | 行动① 搜证选项"（选2处）"A/B/C/D | 决策节点需要 `maxPicks` 字段，且选项可被消耗 |
| 同一地点可重复访问，情报递进 | 酒馆出现 3 次（D1/D2/D4），码头勘查 3 次 | 台词要按"第几次访问"分层，需要 `visitIndex` 与 `once` 控制 |
| 信息影响后续 NPC 态度 | 警探"愣住，随即喊人撬开"→ 之后主动给情报 | 需要 NPC 关系值 / 信任标记，台词条件依赖它 |
| 关键情报来自物证而非对话 | 短函、纸条、妻子的信、十二封通信 | 文档类文本要进同一张表，用 `type` 区分，否则线索系统割裂 |
| 存在失败分支 | 律师"法官允许保释但限制出境"；证据链有强弱 | 同一场景需要多套变体台词，靠条件与优先级择一 |
| 暗线独立于主线 | 主编的灰色交易、生母线索 | 需要 flag 命名空间隔离（`main.*` / `side.*` / `hidden.*`），避免暗线台词被主线条件误触发 |

## 二、核心设计决策：双层条件模型

这是整个结构里最重要的一点。

如果台词条件直接写"玩家历史选择链"，条件会组合爆炸——七日 × 每天 3 次行动 × 每次 4 个选项，理论路径数是天文数字，任何一条台词都要写一长串串行判断。

所以分两层：

```
第 1 层（原始层）：ChoiceLog —— 忠实记录玩家的每一次选择
        ↓ 由 Effect 规则实时折叠
第 2 层（派生层）：GameState —— flags / items / npcState / relationship
        ↓
台词条件 99% 只查第 2 层；极少数关键分岔才直接查第 1 层
```

**派生层承担绝大多数条件判断。** 例如"玩家在 D1 选了 A（夹层）"不会写进台词条件，而是写成 `main.found_pink_shards = true`；台词只问这个 flag。

**原始选择链只在两种情况下直接查询：**
1. 需要判断**顺序**（先问过老板娘、再去找警探 → 警探台词不同）
2. 需要判断**具体哪一天做过哪件事**用于回忆/对质（法庭上律师反问"你哪天去过我的办公室？"）

对应结构里的 `conditions.chain` 字段，支持三种匹配语义（见第四节）。

## 三、四张表 + 一份枚举

台词库落地为四类实体，共用一套枚举字典。

```
DialogueBank
├── enums          枚举字典：npc / location / timeSlot / event / flag / item
├── lines[]        DialogueLine     —— 台词条目（核心表）
├── choiceNodes[]  ChoiceNode       —— 决策节点（a/b/c/d 选项定义）
└── docs[]         DocumentLine     —— 物证/文书文本（复用 DialogueLine 结构）
```

### 3.2 DialogueLine —— 台词条目（核心结构）

```jsonc
{
  // ── 标识 ────────────────────────────────────────
  "id": "DL_NOB_MANSION_D4_018",      // 见第五节编号规范
  "type": "dialogue",                 // dialogue | narration | document | inner
  "version": "1.0",

  // ── 谁 / 在哪 / 何时 ─────────────────────────────
  "npc": "young_noble",
  "location": "mansion_study",
  "time": {
    "day": 4,                         // 1..7；null = 不限日
    "slot": ["afternoon"],            // 数组 = 多时段均可
    "weather": "rainy",               // 可 null，用于氛围变体
    "visitIndex": 1                   // 第几次进入该场景；null = 不限
  },
  "event": "F2_mansion_photo",

  // ── 怎么被触发 ───────────────────────────────────
  "trigger": {
    "type": "forced_node",
    // forced_node   强制节点，条件恒真，优先级最高
    // choice_response 玩家选了某选项后的 NPC 回应
    // enter_scene   进入场景自动播
    // item_inspect  玩家查看某物证
    // npc_initiative NPC 主动搭话（依赖状态阈值）
    // idle_fallback 无内容可播时的兜底
    "nodeId": null,                   // enter_scene 时填场景节点
    "choiceNodeId": null,             // choice_response 时填决策节点
    "optionId": null,                 // choice_response 时填 a/b/c/d
    "itemId": null                    // item_inspect 时填物证 id
  },

  // ── 什么情况下才说（关键）─────────────────────────
  "conditions": {
    "requiresFlags":   ["main.case_opened"],
    "forbidsFlags":    ["main.noble_dead"],
    "requiresItems":   ["old_silver_photo"],
    "forbidsItems":    [],
    "npcState": {                     // 该 NPC 自身状态
      "young_noble": { "present": true, "exposed": false }
    },
    "relationship": {                 // 关系值阈值
      "young_noble": { ">=": 2 }
    },
    "chain": {                        // ← 直接查原始选择链（少用）
      "mode": "ordered_all",          // all | any | ordered_all | ordered_any | count
      "entries": [
        { "node": "CN_D2_TAVERN_INTEL", "option": "c" },
        { "node": "CN_D4_MANSION_TALK", "option": "b" }
      ],
      "minCount": null,
      "withinDays": null              // 限制这些选择发生在第几天内
    },
    "actionBudget": { "remaining": { ">=": 1 } }   // 行动配额条件
  },

  // ── 播什么 ────────────────────────────────────────
  "priority": 80,                     // 多条命中时取最高；相同则按 index
  "once": true,                       // 只播一次
  "group": "F2_photo_reveal",         // 同组内互斥，只播一条（做变体用）
  "text": "",                         // ← 台词正文，留白待填
  "summary": "从书下抽出旧照片递过来，说是在文件里发现的，不知道是谁",
  "delivery": {
    "emotion": "restrained",
    "tone": "low",
    "action": "递出照片",             // 伴随动作/舞台指示
    "sfx": null,
    "portrait": "nob_neutral"
  },
  "target": "player",                 // 说话对象；可为其他 npcId（NPC 互相对话）

  // ── 说完之后 ──────────────────────────────────────
  "effects": {
    "setFlags":   ["hidden.photo_acquired"],
    "addItems":   ["old_silver_photo"],
    "removeItems": [],
    "relationship": { "young_noble": 1 },
    "npcState":   {},
    "unlockNodes": [],
    "advanceDay": false,
    "consumeAction": false
  },

  // ── 后续走向 ──────────────────────────────────────
  "next": {
    "type": "choice_node",            // line | choice_node | scene | ending | null
    "id": "CN_D4_MANSION_TALK"
  },

  "fallback": "DL_NOB_MANSION_D4_040", // 条件不满足时的替代台词
  "tags": ["main", "side_origin", "F2"],
  "notes": ""
}
```

**关于 `group` 字段**：这是处理"同一情境的多个变体"的关键。例如法庭上律师被质问，证据充分 / 证据不足 / 玩家持有"已付清"纸条，是三条互斥台词，同属 `group: "court_lawyer_rebuttal"`，引擎按优先级择一播放，不会连说三句。

### 3.3 ChoiceNode —— a/b/c/d 决策节点

```jsonc
{
  "id": "CN_D1_WHARF_EVIDENCE",
  "day": 1,
  "slot": "morning",
  "location": "wharf_12",
  "event": "D1_action1_search",

  "promptLine": "NAR_D1_WHARF_003",   // 选项出现前的旁白
  "maxPicks": 2,                       // ← 剧本明写"选2处"；单选则为 1
  "allowSkip": false,
  "skipLine": null,
  "repeatable": false,                 // true = 选完可继续选剩余的

  "options": [
    {
      "id": "a",
      "label": "",                     // 选项文案留白
      "summary": "检查货箱夹层，起开底板",
      "requires": {                    // 选项本身可被条件锁死
        "requiresFlags": [],
        "requiresItems": [],
        "relationship": {}
      },
      "hidden": false,                 // true = 条件不满足时不显示（而非置灰）
      "responseLines": ["DL_DET_WHARF_D1_005"],
      "effects": {
        "addItems": ["pink_shard", "red_velvet"],
        "setFlags": ["main.found_pink_shards"],
        "relationship": { "detective": 1 },
        "consumeAction": true
      },
      "consumable": true,              // 选过后置灰
      "next": null                     // null = 回到本节点继续选，直到 maxPicks 用尽
    },
    { "id": "b", "label": "", "summary": "沿地面拖痕追往冷藏库方向", "…": "…" },
    { "id": "c", "label": "", "summary": "找码头工人问口供",          "…": "…" },
    { "id": "d", "label": "", "summary": "翻查货物登记簿 M-412",       "…": "…" }
  ],

  "onExhausted": "DL_DET_WHARF_D1_009", // 配额用尽 / 选择结束后的收束台词
  "onTimeout": null                     // 若有倒计时机制
}
```

`maxPicks` + `consumable` + `onExhausted` 三者配合，才能表达剧本里"搜证选项（选2处）"这种非标准单选。

### 3.4 DocumentLine —— 物证与文书

结构复用 DialogueLine，差异固定为：

```jsonc
{
  "type": "document",
  "npc": "narrator",                  // 或实际书写者，如 "manager_wife"
  "trigger": { "type": "item_inspect", "itemId": "manager_wife_letter" },
  "text": "",                         // 文书正文留白
  "summary": "经理妻子留下的信：丈夫为还债受人指使，往来信函藏在肯特郡阁楼",
  "delivery": { "emotion": null, "action": null, "portrait": null,
                "render": "handwritten_letter" },   // 渲染样式
  "effects": { "setFlags": ["main.know_kent_address"],
               "addItems": ["kent_address_clue"] }
}
```

**为什么要放进同一张表**：剧本里破案的四条关键证据中，有三条（妻子的信、匿名纸条、往来通信）是文书而非对话。如果分表管理，"线索解锁 → NPC 台词变化"这条链路就要跨系统查询。统一表 + `type` 字段区分，`effects.setFlags` 是共用的，条件系统也共用。

## 四、条件求值规则

### 4.1 历史选择链的四种匹配语义

| mode | 含义 | 典型用途 |
|---|---|---|
| `all` | 列出的选择全都发生过（不论顺序） | "玩家既去过海关又去过警局" |
| `any` | 至少发生过一条 | "玩家用任意方式得知了冷藏库" |
| `ordered_all` | 全部发生，且顺序与列出的一致 | "先从老板娘处拿到纸条、再去警局" → 警探反应不同 |
| `count` | 命中数 ≥ `minCount` | "搜集到 3 条以上关于律师的证据" → 法庭强势分支 |

`withinDays` 用于把链限制在某几天内，避免 D1 的旧选择在 D7 还生效。

### 4.2 多条命中时的仲裁

```
1. 收集当前场景下所有 trigger 匹配的候选台词
2. 逐条求值 conditions（任一子条件不满足则淘汰）
3. 按 group 去重：同组只保留 priority 最高的一条
4. 全局按 priority 降序、再按 id 升序排列
5. 过滤掉 once=true 且已播放过的
6. 播放队首；若队列为空 → 播 idle_fallback；再无 → 静默
```

`priority` 建议区间：
- 强制节点 F1/F2/F3 → `100`
- 主线关键推进 → `80`
- 选项回应 → `60`
- 状态变体 / 暗线 → `40`
- 重复访问递进情报 → `30`
- 兜底闲聊 → `10`

## 六、状态与 flag 命名空间

```
main.*     主线进度        main.found_pink_shards / main.recovered_diamond / main.know_kent_address
side.*     支线            side.customs_record / side.tunnel_found
hidden.*   暗线（不可逆）  hidden.photo_acquired / hidden.hair_sample / hidden.editor_bribe
npc.*      NPC 状态        npc.detective.trust / npc.lawyer.exposed / npc.manager.arrested
sys.*      系统            sys.day / sys.actions_left / sys.visit_count.<location>
```

**暗线单独命名空间的原因**：身世线与主编线一旦触发就不应回退，且它们的台词条件绝不能被主线 flag 意外满足。用前缀隔离后，可以批量对 `hidden.*` 做"只置真、不清除"的约束校验。

关系值建议范围 `0–5`，`trust` 与 `hostility` 分两个维度，避免"警探讨厌你"和"律师警惕你"用同一个数值。

## 七、运行时数据结构（玩家存档）

台词库是静态数据，存档是动态状态。两者分离：

```jsonc
{
  "saveId": "…",
  "scriptVersion": "1.0",
  "sys": { "day": 4, "slot": "afternoon", "actionsLeft": 2, "weather": "rainy" },

  // ← 第 1 层：原始选择链，只追加不修改
  "choiceLog": [
    { "day": 1, "node": "CN_D1_WHARF_EVIDENCE", "option": "a", "ts": "…" },
    { "day": 1, "node": "CN_D1_WHARF_EVIDENCE", "option": "d", "ts": "…" },
    { "day": 2, "node": "CN_D2_POLICE_TALK",    "option": "c", "ts": "…" }
  ],
  "visitCount": { "wharf_12": 3, "tavern": 2 },

  // ← 第 2 层：派生状态，由 effects 累加得出
  "flags": ["main.found_pink_shards", "main.registry_gap", "hidden.photo_acquired"],
  "inventory": ["pink_shard", "old_silver_photo", "seal_ring"],
  "npcState": {
    "detective":    { "trust": 3, "present": false },
    "young_noble":  { "trust": 2, "present": true },
    "lawyer":       { "exposed": false }
  },

  "playedLines": ["DL_NOB_MANSION_D4_010", "…"],   // once 去重用
  "currentNode": "CN_D4_MANSION_TALK"
}
```

`choiceLog` 永不压缩——它是 `conditions.chain` 的数据源，也是回放/调试/成就系统的依据。

## 十、自动校验结果

生成脚本对全库做了五项一致性检查，结果：

| 检查项 | 结果 |
|---|---|
| ID 重复 | 无 |
| 悬空引用（promptLine / responseLines / onExhausted / ending.lines 指向不存在的台词） | 无 |
| 未登记枚举（条件或效果引用了 enums 中不存在的 flag / item / npc / location / event） | 无 |
| **死条件**（被条件引用、但没有任何环节会置位的 flag） | 无 |
| 兜底覆盖（每个 `idle_fallback` 均为 `once=false`，可无限重播） | 20/20 通过 |

第 4 项是这套校验里最有价值的一条。它抓到过一个真实缺陷：`hidden.wife_testified` 被结局 `END_WIFE_TESTIFY` 引用，但没有任何选项会设置它——意味着"经理妻子出庭"这条支线永远进不去。修法是把 D4 旅馆节点的 c/d 两个选项改成后果不同：c 先承诺保护再请她出庭（置位 `wife_testified`），d 不做承诺直接要求（她拒绝连夜离开）。两个选项原本共用一条回应台词，也一并拆成了 `DL_WIF_HOTEL_D4_013` / `_014`。

**建议把这几项检查固化成 CI**：每改一次台词库就跑一遍，死条件和悬空引用在文案阶段几乎无法靠肉眼发现。

另有一项非错误的提示：46 个 flag 中有 24 个已被置位但尚未被任何条件引用（如 `main.absence_pattern`、`main.dover_marginalia`、`hidden.face_resemblance`）。这些是**给文案预留的钩子**——剧本里它们确实构成了推理链，但当前还没有台词拿它们做条件。可以精简，也可以留着扩展变体台词。

### 10.1 随机通关模拟（500 次）

光有静态校验不够，还要确认这套数据**真能从第一天跑到第七天、不会卡死**。所以写了一个模拟器：随机走每一天的每个决策节点，应用所选选项及其回应台词的全部效果（flag / 道具 / 关系值），跑满七日后判定结局。

| 指标 | 结果 |
|---|---|
| 死锁节点（某节点所有选项条件都不成立、又无兜底） | **0** |
| 结局可达性 | `END_LOSS` / `END_CANON` / `END_WIFE_TESTIFY` 三者均被触达 |
| 正典结局占比（随机乱选下） | 约 26%，符合"乱选较难拿到圆满结局"的预期 |

这次模拟又抓到一个静态校验发现不了的缺陷：**法庭举证节点 `CN_D7_COURT_EVIDENCE` 的四个选项全部带前置条件**（妻子的信 / 戴面纱女子 / 已付清字条 / 经理供词）。如果玩家前六天什么关键证据都没拿到，到了法庭就会发现**四个选项全是灰的、无话可说**——这是硬死锁。修法是给该节点开 `allowSkip` + `skipLine`（指向警探的"证据不足"台词 `DL_DET_COURT_D7_052`），保证证据全无时庭审仍能以"举证不足"走完，落到保释结局。

> 这条经验值得记住：**带 `requires` 的多选节点，必须保证"全不满足"时仍有出路**（skipLine 或一个无条件选项）。静态校验查不出这种缺陷，只有跑模拟才会暴露。

### 10.2 一处需要留意的模拟器局限

模拟结果里 `main.lawyer_bailed` 这个 flag 始终没被置位——这是**模拟器本身的局限，不是数据缺陷**。法官的两条判决台词（`DL_JDG_COURT_D7_002` 定罪 / `_003` 保释）是 `npc_initiative` 触发、靠 `group=judge_verdict` 互斥择一，而我的模拟器只建模了 `forced_node / enter_scene / item_inspect / ending` 四类触发，没有完整实现 group 仲裁，所以没去置位判决 flag。真实引擎里 `judge_verdict` 组有一条恒真兜底（`_003`），判决必然产生。若要让模拟更逼真，需要补上 `npc_initiative` 与 group 互斥的求值逻辑。

## 十一、实现建议（避坑）

1. **先建 flag 表再写台词。** 台词条件全部依赖 flag，flag 命名一旦中途改，全库条件失效。第六节的 flag 清单（46 条）已冻结在数据文件的 `enums.flag` 里，改动请走版本递增。

2. **`text` 与 `summary` 分离，是有意的。** 当前 228 条的 `text` 全为空、`summary` 全部填好。文案可以在不看结构的情况下按 `summary` 填 `text`，策划也能在 `text` 全空时跑通全流程做逻辑验证。请保留这个分工。

3. **每条台词都必须有兜底。** 最容易出的 bug 是"玩家进了场景，所有台词条件都不满足，NPC 一句话不说"。`idle_fallback`（priority 10，条件恒真，`once=false`）是硬性要求，每个 NPC × 每个可进入场景至少一条。

4. **`group` 互斥比 `priority` 更重要。** 108 条台词带 group。变体台词如果只靠优先级，条件写松一点就会连播三条。同组互斥是保险。

5. **变体组内要有一条恒真兜底。** `DL_LAW_COURT_D7_041` 就是为此加的：律师庭审的所有变体条件都不满足时，它保证法官不会面对一片沉默。同理 `DL_JDG_COURT_D7_003`（保释判决）作为 `judge_verdict` 组的兜底恒可播——**判决必须有结果，不能因为证据条件全不成立就没有宣判**。

6. **警探的"嗯"不要写进 `text`。** 剧本明写这是人物口癖，已放在 `enums.npc[detective].verbalTic`，由渲染层统一前置。否则文案改口癖时要动 48 条记录。

7. **`choiceLog` 只追加、永不修改。** 即使派生状态能重算，原始链也要保留——它是调试"为什么这句台词没触发"的唯一依据。

8. **注意剧本里的时序陷阱。** D7 的十二封信在**庭后**才到手，不能用于庭审条件（见 8.4 的警示框）。类似的还有 D5 隧道需要 D3 的钥匙（`side.cold_storage_key`）——跨日依赖要用 flag 显式表达，并在选项上配 `requires`，否则玩家会卡在打不开的铁门前。

9. **失败分支要提前占位。** `DL_NOB_MANSION_D6_040`（钻石未追回）、`DL_LAW_COURT_D7_017`（证据薄弱）、`DL_LAW_COURT_D7_020`（辩方胜诉）、`DL_JDG_COURT_D7_003`（保释）都已建好。剧本给的是成功结局，但 D6 追回钻石、D7 举证两步都可能失败，不要等文案阶段才发现结构不支持。
